# 66qn 开放平台接口协议 v1

版本：`v1.0`（2026-10-23）
适用对象：Minecraft 服务端模组、第三方机器人、外部应用、AI Agent
文档地址：https://66qnmc.top/open-platform/protocol-v1.md
维护方：66qn 服务器管理组

本协议只描述"怎么调、返回什么、错了怎么办"。实现方只需支持 HTTPS + JSON，无 SDK 要求。

---

## 1. 端点与传输

| 项 | 值 |
|---|---|
| 请求方式 | `POST` |
| 端点 | `https://iywntwllhjbubmhtacdp.supabase.co/rest/v1/rpc/open_api` |
| 必带请求头 | `apikey: <项目 anon key>`、`Content-Type: application/json` |
| 协议要求 | 仅 HTTPS，禁止明文 HTTP 转发 |
| 响应类型 | `application/json`，单个对象 |

anon key 是 Supabase 的公开密钥（配合行级安全使用），**不是**本接口的凭据；真正的凭据是请求体里的 `p_uid`。

模组侧获取 anon key：向管理组申请，或在站点 `config.js` 中读取（该文件公开可访问）。

---

## 2. 鉴权与账号模型

每个接入方持有一把 **UID**，格式 `ok_` + 48 位十六进制字符。UID 等同密码：

- 由管理员在后台「开放平台 → 创建账号」发放，或由玩家在站点「AI 技能」页自助领取；
- 明文只在发放那一刻展示一次，服务端只存加密值和哈希；
- 泄露后无法自助更换，必须联系管理员停用并重发。

一把 UID 对应一个开放账号，账号带有：

| 属性 | 说明 |
|---|---|
| `public_id` | 对外标识，形如 `op_xxxxxxx`，可用于日志对账，不含敏感信息 |
| `bind_username` | 绑定的玩家昵称。绑定后**只能操作该玩家**；为空表示可指定任意玩家（仅管理员发放的高权限账号会有） |
| 权限位 | `get_info` / `get_power` / `checkin` / `add_power` / `deduct_power` 五项独立开关 |
| `status` | `active` 或 `disabled`；`disabled` 时所有调用直接失败 |

自助领取的账号（玩家自己领的）默认权限是：可查信息、可查电力、可签到，**不可加电、不可扣电**，且只能操作领取者本人。模组需要加/扣电能力时，必须由管理员单独建号并开权限，不要指望玩家自助 UID 能做到。

---

## 3. 请求格式

```json
{
  "p_uid": "ok_xxxx...",
  "p_action": "get_power",
  "p_username": "steve",
  "p_amount": 100
}
```

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `p_uid` | string | 是 | 凭据。缺失或错误一律按"UID 无效"处理 |
| `p_action` | string | 是 | 动作名，见第 4 节 |
| `p_username` | string | 视动作 | 目标玩家昵称。账号已绑定玩家时可省略（自动用绑定值）；此时传别的昵称会被拒绝 |
| `p_amount` | integer | 加/扣电必填 | 取值 `1` ~ `100000`，正整数 |

昵称匹配为**大小写不敏感**的精确匹配，不做模糊查询、不支持游戏 ID 查询。

---

## 4. 动作一览

| `p_action` | 需要权限位 | 必填参数 | 语义 |
|---|---|---|---|
| `ping` | 无 | 无 | 连通性 + 凭据有效性自检。**不计入首次安装奖励**，不查玩家 |
| `get_info` | `get_info` | 绑定可省 `p_username` | 查询账号资料 |
| `get_power` | `get_power` | 同上 | 查询当前电力余额 |
| `checkin` | `checkin` | 同上 | 每日签到，+100 电力。同一天重复调用不算错，`gained` 返回 0 |
| `add_power` | `add_power` | `p_username` + `p_amount` | 给玩家增加电力 |
| `deduct_power` | `deduct_power` | `p_username` + `p_amount` | 扣减玩家电力，余额不足直接失败 |

### 成功响应

统一带 `"ok": true`。各动作返回字段：

`ping`
```json
{"ok":true,"public_id":"op_xxxxxxx","name":"我的机器人","bind_username":"steve"}
```

`get_info`
```json
{"ok":true,"username":"steve","game_id":"Steve_01","bio":"简介文本",
 "power":5300,"status":"active","created_at":"2026-10-11T12:27:50.227576+00:00"}
```

`get_power`
```json
{"ok":true,"username":"steve","power":5300}
```

`checkin`
```json
{"ok":true,"username":"steve","gained":100,"power":5400}
```
当日已签到：`{"ok":true,"username":"steve","gained":0,"power":5400}`

`add_power` / `deduct_power`
```json
{"ok":true,"username":"steve","power":5500,"amount":100}
```
`amount` 是**带符号的实际变动量**：加电为正，扣电为负（如 `-100`）。`power` 是变动后的最新余额，调用方应以它为准更新本地缓存。

### 首次安装奖励

玩家自助账号的**第一次非 ping 且成功**的调用，会额外给绑定玩家发放 60000 电力安装奖励，响应里多一个字段：

```json
{"ok":true,"username":"steve","power":65400,"gained":100,"install_reward":60000}
```

该奖励每个账号只发一次。`ping` 不触发。管理员发放的账号不触发。

## 5. 失败响应与错误语义

所有业务失败都返回 HTTP 200 + `"ok": false` + 中文 `error` 文案，**不要按 HTTP 状态码判断业务结果**。

| `error` 文案 | 含义 | 调用方应怎么做 |
|---|---|---|
| `UID 无效` | 凭据不存在 | 停止重试，提示重新配置 UID |
| `该开放账号已停用` | 管理员已禁用该账号 | 停止重试，联系管理员 |
| `调用太频繁（每小时限 120 次），请稍后再试` | 触发限流 | 指数退避，至少等 60 秒；不要立即重试 |
| `未指定玩家昵称，且该开放账号未绑定玩家` | 缺 `p_username` | 补参数后重试一次 |
| `该开放账号只能操作绑定的玩家：xxx` | 越权操作他人 | 停止，这是权限边界，不是临时错误 |
| `找不到玩家：xxx` | 昵称不存在 | 检查昵称拼写，不要循环重试 |
| `该玩家已被封禁` | 目标玩家状态为 banned | 停止该玩家的相关流程 |
| `电力数量需在 1-100000 之间` | 参数越界 | 修正参数 |
| `电力不足，当前 N` | 扣减超额 | 用返回的 `N` 作为上限，或改为提示玩家 |
| `未知操作：xxx` | `p_action` 拼错 | 修正代码 |
| `该开放账号未开通「××」权限` | 权限位未开 | 联系管理员开权限，重试无意义 |

HTTP 层面的异常另算：`401/404` 一般是端点或 `apikey` 写错，`5xx` 是数据库侧故障，这类情况可以重试（但见下一节关于写操作重试的限制）。

## 6. 限流、幂等与并发（务必读）

**限流**：每个 UID 每小时最多 120 次调用，**失败的调用也计数**。模组侧应当自己做缓存和合并，不要每次玩家动作都打一次接口。

**幂等：本版本没有幂等键。** 这是 v1 最重要的限制：

- `add_power` / `deduct_power` / `checkin` 一旦被重复调用，就会**重复生效**；
- 因此**写操作超时或网络异常后，禁止自动重试**。正确做法是：先调 `get_power` 或查自身业务流水确认，再决定是否补发；
- 只读动作（`get_info` / `get_power` / `ping`）可以随意重试。

**并发**：扣电的余额校验和扣减不是同一原子步骤，两个并发扣电请求理论上可能同时通过余额校验、把余额扣成负数。模组侧要求：

- 对同一玩家的加/扣电**串行执行**，不要并发；
- 每次写操作后以响应里的 `power` 为准刷新本地值，不要自己加减。

**审计**：所有调用（含失败）都会落库记录，包含动作、目标玩家、金额、成败、错误文案和账号累计调用次数。管理后台「开放平台」可查。模组侧也应自行记录请求流水，便于对账。

## 7. 接入流程

1. 向管理组说明用途，申请 UID，并明确需要哪几项权限（默认只给只读 + 签到）；
2. 用 `ping` 验证凭据与网络；
3. 用 `get_power` 验证权限位是否已开；
4. 上线写操作前，先在测试账号上跑一遍 `add_power` / `deduct_power`，确认自己正确解析了带符号的 `amount`；
5. 把 UID 存在**服务端配置**里，绝对不要写进发给 Minecraft 客户端的资源包、插件配置分发件或任何前端代码。

---

## 8. 兼容性承诺

- 本协议版本号写在文档首行。字段只增不改：已发布字段的名称、类型、语义不会变更；
- 新增动作或字段不升主版本号，接入方解析时应忽略未知字段；
- 破坏性变更会升主版本（v2）并保留 v1 至少 6 个月；
- 权限位、限流阈值可能按账号单独调整，以管理组发放 UID 时的说明为准。

## 9. 已知限制与后续版本计划

| 编号 | 现状 | 计划 |
|---|---|---|
| L1 | 无幂等键，写操作不可安全重试 | v1.1 增加 `p_request_id`，同一 UID 下重复请求返回首次结果 |
| L2 | 扣电余额校验与扣减非原子，并发可扣成负数 | v1.1 后端改为行锁或条件更新（`where power >= amount`） |
| L3 | UID 为长期有效静态凭据，无过期与轮换 | v1.2 支持有效期与自助轮换 |
| L4 | 无按 IP 白名单、无 HMAC 请求签名 | v1.2 提供可选签名模式 |
| L5 | 单次调用单动作，无批量接口 | 视需求评估 v1.1 批量端点 |

有对接入方式的建议或发现文档与实际行为不一致，联系管理组（QQ 群见站点首页）。
